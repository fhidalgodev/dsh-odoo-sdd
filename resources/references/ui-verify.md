# odoo_ui_verify — browser verification for QA

`odoo_ui_verify` runs a flow in a REAL browser and fails it when the INTERFACE
reports an error. It exists because RPC evidence cannot see the screen: an
`odoo_execute` call can return OK while the user is looking at a traceback.
The same engine as `odoo_manual`/`odoo_video` drives the browser, but after
EVERY step the UI probe is drained — a finding flips the step to `error` and
freezes an `*-error.png` of what the user actually saw.

Artifacts live in `<specDir>/ui-verify/`:

```
ui-verify/
├── flows.json          # the QA-authored flows (operation=plan drafts it)
├── report.json         # operation=run verdict — read by the verify gate
├── crawl-report.json   # operation=crawl verdict (the canon smoke)
├── matrix-report.json  # operation=matrix verdict (per-role evidence)
├── matrix-<login>/     # one workspace per temporary user (its run report + images)
└── images/             # automatic <flow>-<step>-error.png evidence shots
```

## Operations

| operation | what it does |
|---|---|
| `plan` | Drafts one skeleton flow per `ui` row of `test-plan.md` into `flows.json` (create-only merge: existing flows are kept, missing ACs get a skeleton). The skeleton step is deliberately INVALID — lint reports ERROR until the QA writes real steps. |
| `lint` | Structural check of `flows.json` + AC coverage. |
| `crawl` | Generates a read-only smoke from the module canon (`module=` required): opens every menu that launches an act_window, switches through its view_mode, opens the first record and visits the notebook pages. Header buttons are only `expect_visible`-checked, never pressed. Writes `crawl-report.json`. |
| `run` | Executes `flows.json` (`flow=` for one, `from_step=` to resume). Writes `report.json`. |
| `matrix` | Role matrix: creates ONE approved temporary user per group and runs, for each group, only the flows that declare its role. Writes `matrix-report.json`. See [Role matrix](#role-matrix). |
| `status` | Summarizes the persisted reports. |

## flows.json schema

```json
{
  "schema": "dsh-odoo-sdd/ui-verify/flows/1",
  "flows": [
    {
      "id": "ui-ac1",
      "title": "Verify AC1",
      "ac": ["AC1"],
      "roles": { "sales_user": "ok", "portal": "denied" },
      "steps": [
        { "id": "s01", "kind": "menu", "target": { "kind": "menu", "xmlid": "my_module.menu_root" } },
        { "id": "s02", "kind": "switch_view", "view": "form" },
        { "id": "s03", "kind": "expect_state", "value": "Draft" }
      ]
    }
  ]
}
```

- `ac`: the test-plan AC ids this flow proves. A flow earns its evidence line
  only when it completed whole with zero findings.
- `roles`: expected outcome per group xmlid — `"ok"` (the flow must pass
  clean) or `"denied"` (the flow must fail on access evidence). `operation=matrix`
  executes it; lint validates the values and warns when a role-bearing flow has
  no `expect_*` step.
- `steps[].target`: same shape as `odoo_manual` (`{"kind":"url"|"menu"|"xmlid", ...}`).

## Step types and safety

Read-only (always allowed):

`goto`, `menu`, `wait`, `assert`, `screenshot`, `explore`, `confirm`,
`open_row` (`index`, 0-based), `switch_view` (`view`), `search` (`value`),
`click` with `"tab": true` (notebook tab only — generated by the crawl),
`expect_state` (`value`), `expect_field` (`field`+`value`),
`expect_visible` / `expect_hidden` (`field`, `text`, or a raw selector in
`value`).

Action (need `allow_actions=true` AND `confirm_destructive=true`, and are
refused outright when the declared environment is `production`):

`new`, `fill`, `select`, `press`, `click`, `save`, `discard`, `click_text`
(`text`, scoped to `.o_action_manager` or an open modal), `add_line`
(optional `field`).

`drag` and `highlight` are manual/video steps and lint rejects them here.

## Security restrictions

- Same fences as `odoo_manual`: action steps blocked without
  `allow_actions=true`, and `allow_actions` without `confirm_destructive`
  returns `CONFIRM_REQUIRED`. The host guard also classifies
  `operation=run + allow_actions=true` as a mutation.
- `production` environment refuses `run` entirely — even read-only flows —
  and `matrix` as well.
- `matrix` is ALWAYS classified as a mutation by the host guard (it creates
  `res.users` records); it is also refused without a native approval seam.
- The browser is origin-locked to the Odoo base URL (off-origin requests
  abort by design and are NOT findings).
- The session cookie lives in memory only and is never returned. The
  temporary-user passwords the matrix generates never leave process memory
  either — they are absent from reports, audit lines, messages and results.

## Finding kinds

| kind | source |
|---|---|
| `js-error` | uncaught page exception (`pageerror`) |
| `console-error` | error-level console line (favicon/asset-404/websocket noise excluded) |
| `http-5xx` | same-origin response with status ≥ 500 |
| `rpc-error` | HTTP-200 JSON body with `error` on `/web/dataset/call_kw*`, `/web/dataset/call_button`, `/web/action/load`, `/web/webclient/*` |
| `request-failed` | failed same-origin request (origin-lock aborts excluded) |
| `error-dialog` | DOM: the error dialog selector of the version family |
| `danger-notification` | DOM: the danger toast selector |
| `invalid-field` | DOM: `.o_field_invalid` |

`ignore` patterns (regex, validated up front) drop matching findings but the
report counts them in `ignoredCount` — record every ignore justification in
the KB.

## Selectors per Odoo version

| selector | 16 | 17 | 18/19 |
|---|---|---|---|
| error dialog | `.o_dialog_error, .o_dialog_warning` ✔ source-verified | `.o_error_dialog` ✔ | `.o_error_dialog` ✔ |
| danger toast | `.o_notification.border-danger` ✔ | `.o_notification.border-danger` ✔ | `.o_notification:has(.o_notification_bar.bg-danger)` ✔ |
| invalid field | `.o_field_invalid` ✔ | `.o_field_invalid` ✔ | `.o_field_invalid` ✔ |

Verified against the installed sources (`core/errors/*.xml`,
`core/notifications/notification.xml`, view/field code). The exact markers —
including the E2E status of each family — live in `UI_FAMILIES[].verified`
(`src/manual-capture.ts`); an Odoo major without a verified family is refused
rather than guessed.

## Role matrix

`operation=matrix` verifies the `roles` block of `flows.json`. For every group
it runs ONLY the flows that declare that group:

- `"ok"` — the flow must complete whole with zero findings.
- `"denied"` — the flow passes ONLY on access evidence: an `error-dialog` or
  `rpc-error` whose message matches `access|acceso|访问|not allowed|AccessError`
  (case-insensitive), or a navigation/click step whose target was never
  rendered (a menu/button the group cannot see — `no view rendered` / selector
  timeout). A clean run FAILS as "expected denied, but the flow ran"; a
  non-access traceback FAILS as a defect, not as the denied path.

Lifecycle, fail-closed:

1. Every group xmlid (plus `base.group_user`) is resolved in `ir.model.data`
   FIRST — a missing one is `BLOCKED` before any user exists.
2. The browser is resolved (a machine without one records `NEEDS_BROWSER`).
3. Native human approval — the reason names the `sddqa_*` logins, groups,
   target and environment. No service, or anything but `allowed-once` ⇒
   `NOT_APPROVED` and **zero** `res.users.create`.
4. One user per group: `sddqa_<n>_<rand4>`, name `SDD QA <group>`, groups
   `base.group_user` + the target group (`[[6,0,ids]]` on the canon group
   field), a random 24-byte password kept only in memory, and
   `no_reset_password`/`tracking_disable` context so no mail is sent. These
   creations do NOT pass through the approval journal — the native approval
   IS the control.
5. Each user logs in (`/web/session/authenticate`) and runs its flows.
6. `finally` ALWAYS cleans up: `unlink` first, `write {active: false}` as the
   fallback. If both fail the verdict is `CLEANUP_PENDING` and the surviving
   ids/logins are named in the report and the result.

`matrix-report.json` (`dsh-odoo-sdd/ui-verify-matrix/1`) records `verdict`
(`PASSED|FAILED|PARTIAL|CLEANUP_PENDING|NEEDS_BROWSER|NOT_APPROVED`), per group
the login, uid, per-flow `expected`/`observed`, findings and captures, plus
`createdUserIds` and `cleanup` (`none|deleted|archived|pending`). Passwords and
cookies never appear in it. Creation and cleanup are written to
`.sdd/audit.jsonl`. If the process dies between create and cleanup, `sddqa_*`
users may remain — find them with a `login like 'sddqa_%'` search and delete
them; nothing detects them automatically.

## report.json

`schema: "dsh-odoo-sdd/ui-verify/1"`, `mode` (`flows`|`crawl`), `verdict`
(`PASSED`|`FAILED`|`PARTIAL`|`NEEDS_BROWSER`), `startedAt`, `serverVersion`,
`environment?`, `flowsHash`, `ignore`, `ignoredCount`, `originLocked`,
`flows[]` (per step: status, findings, `capture` path of the error shot),
`evidence` (AC → suggested test-plan line). The `sdd_phase succeed` gate
reads `report.json` (and `crawl-report.json`/`matrix-report.json` when
present): missing or FAILED/PARTIAL is a gap, NEEDS_BROWSER is documented but
never a pass. When `flows.json` declares `roles`, a MISSING
`matrix-report.json` is a gap of its own; PASSED closes it.

## Limits

- No drag & drop, no file downloads, no PDF preview checks, no third-party
  widgets (map, gantt, spreadsheet) — the probe sees DOM/console/network
  errors, not widget-specific correctness.
- A `NEEDS_BROWSER` report is evidence of a REQUIREMENT, not of a result.
- The crawl visits what the canon evidences; it never invents routes.
